# OMP Integration Findings

## Summary

Current OMP extension APIs provide strong pre-effect coverage for registered tools in the main session and unrestricted child sessions. They do not form a universal security boundary: restricted subagents intentionally discard extensions, arbitrary execution has ambient capabilities after dispatch, and some core mutations bypass the tool registry.

## Registered tool interception

`tool_call` is emitted before execution and may block the call or return revised input. The event occurs during argument preparation, before concurrent scheduling, tool execution, persistence, and native approval handling.

Once a session's registry is wrapped, the event covers:

- built-in tools;
- extension tools;
- custom tools;
- MCP tools;
- device operations reached through a registered tool, including `write` calls targeting `xd://` devices.

Installed-source evidence:

- `session/agent-session.ts` constructs session tools and extension plumbing.
- `session/session-tools.ts` uses `ExtensionToolWrapper` from `#wrapRuntimeTool` when an extension runner exists.
- Extension documentation describes `tool_call` and `tool_result` in `omp://extensions.md` around the tool lifecycle section.

This is the primary no-fork enforcement seam.

## Interactive commands

- `user_bash` can replace execution with a synthetic result and therefore block direct interactive shell commands.
- `user_python` provides the equivalent interception for direct Python input.
- `input` can return `{ handled: true }` before normal input handling, permitting pre-dispatch checks for built-in slash commands.

A direct user command normally supplies strong explicit authorization, but protected global policy may still deny it. Commands generated by an extension or other non-user source must not inherit the same authority.

## Tool shadowing

An extension can register a tool with the same name as a built-in and delegate through `ctx.invokeTool`. Delegation is constrained to the same tool and avoids recursive re-gating. This can wrap a specific built-in, but generic `tool_call` interception is simpler and covers future registered tools without name shadowing.

## File write and delete fallbacks

The process-wide file fallbacks are not generic policy hooks.

`registerFileWriteFallback` runs only after a normal byte-oriented `write`, `edit`, or `apply_patch` path fails with `EPERM`, `EACCES`, or `EROFS`. It does not intercept successful writes and does not cover every mutation mechanism.

Known exclusions include:

- archive member updates;
- SQLite row operations;
- ACP remote writes;
- LSP workspace edits and applied code actions;
- formatter or other subprocess writes.

The delete fallback has the same permission-failure character. These registries can broker denied writes from restricted subagents, but they cannot implement general semantic enforcement.

## Native approval model

Tools declare `read`, `write`, or `exec` approval classes, and user policy resolves each tool to `allow`, `deny`, or `prompt`.

Observed behavior:

- explicit user denial remains authoritative;
- unrestricted subagents may use permissive ordinary-tier defaults;
- headless subagents cannot satisfy an interactive prompt, so prompt behaves as rejection;
- ACP tools use the same approval mechanism.

Native approval is a useful coarse backstop, not semantic policy. Allowing `bash` does not constrain the command's filesystem, network, or subprocess activity. `eval` can also launch operations through its host runtime.

## Subagents

OMP creates a distinct extension runner for child sessions when extensions are available.

The task executor passes parent-discovered extension paths and prepared extensions to unrestricted subagents. When `restrictToolNames` is active, it deliberately passes empty extension collections. The structured-subagent path follows the same rule.

Source evidence in `task/executor.ts` shows the conditional assignment around the child-session construction: restricted sessions receive empty `preloadedExtensionPaths` and `preloadedPreparedExtensions`; unrestricted sessions receive the parent values.

Consequences:

- Main session: individual registered tool calls are enforceable.
- Unrestricted child: the installed plugin can enforce individual registered tool calls.
- Restricted child: only the parent's `task` dispatch is policy-gated; child calls are not seen by the plugin.
- A restricted child with mutating tools is therefore a bypass unless static native approval denies those tools or OMP gains a process-wide trusted policy hook.

The parent adapter should classify the delegated task, preserve session lineage, and include the applicable policy snapshot or summary. It must not claim this is equivalent to per-action child enforcement.

## Broad execution tools

`bash` and `eval` are registered tools, so the complete script or code body is available before dispatch. The policy can allow, prompt, revise, or deny that outer action.

After dispatch, nested effects are not separately visible:

- subprocess creation;
- filesystem access;
- network requests;
- browser calls made from evaluation code;
- browser `run` code;
- native library operations.

These surfaces are **dispatch-gated**, not sandboxed. A model may classify the requested code and its apparent targets, but dynamic behavior remains outside the plugin's mediation.

## LSP and device-backed operations

A direct `write` request to an `xd://lsp`, `xd://ast_edit`, or `xd://debug` device is still intercepted as the outer registered `write` tool call. The policy can inspect and gate the requested device action.

If an allowed LSP action subsequently edits several files, the plugin does not receive a separate final-byte decision for every file. This is another dispatch boundary. An upstream action hook should expose resolved targets before mutation when practical.

## Direct core mutations

Some built-in command/controller code calls filesystem APIs directly instead of invoking a registered tool. Examples found during source inspection include directory creation in `command-controller.ts` for `/move` and direct todo export writes in `todo-command-controller.ts`.

The `input` event can reject the originating interactive slash command before built-in handling. It cannot inspect each deeper side effect after execution begins. Background or internally initiated mutations without an input or registered-tool event remain uncovered.

## Project extension trust

Current source reports project trust unconditionally through `isProjectTrusted()`. Project-local extensions are executable code with ambient authority. A plugin cannot be a hard security boundary against malicious code already trusted and loaded by the host.

A future process-wide policy gate must be registrable only by profile/user-trusted packages, never by a project-local extension.

## Coverage matrix

| Surface | Current plugin coverage | Notes |
| --- | --- | --- |
| Main-session registered tools | Enforced | Pre-effect `tool_call` |
| Built-in, custom, extension, MCP tools | Enforced | Once registry is wrapped |
| `xd://` device request | Enforced at dispatch | Downstream multi-file effects are not individually gated |
| Unrestricted subagent tools | Enforced | Parent extensions are propagated |
| Restricted subagent tools | Dispatch-gated | Parent `task` call only |
| Interactive shell/Python | Enforced at dispatch | `user_bash`, `user_python` |
| Slash commands | Enforced at input dispatch | Deeper effects are not individually gated |
| `bash`/`eval` nested behavior | Dispatch-gated | No process containment |
| Provider-side tools | Uncovered locally | Execution is outside local registry |
| Direct background/core mutations | Uncovered unless preceded by input | Needs upstream hook |
| Project-local extension code | Outside security boundary | Host treats it as trusted code |

## No-fork conclusion

A marketplace plugin can deliver meaningful enforcement today. Universal coverage requires a small upstream OMP capability, not a maintained fork: a trusted, process-wide `PolicyGate` called for every action from the central approval/execution path, including restricted sessions and direct core mutations.
